Glossary

Reference of terms, architectural entities, and technologies used in the zkpool-mesh project.
Terms are grouped by topic and include links to official documentation.

1. Zero-Knowledge Cryptography (ZK)

Section titled “1. Zero-Knowledge Cryptography (ZK)”

ZK proof (zero-knowledge proof)

Section titled “ZK proof (zero-knowledge proof)”

A cryptographic method for proving knowledge of a secret without revealing the secret itself.

In zkpool-mesh, a user proves ownership of the secrets for one of the deposit notes in the pool without revealing the note’s index or contents, breaking the link between the deposit transaction and withdrawal transactions.

Circuit (ZK circuit)

Section titled “Circuit (ZK circuit)”

A program describing a provable statement as arithmetic constraints over a finite field.
It consists of public inputs, private inputs, and a set of mathematical constraints.

The project uses the withdrawal circuit, which verifies five statements (C1–C5).

Public input

Section titled “Public input”

A value known to both the prover and the verifier.
Declared in Noir using the pub keyword.

The withdrawal circuit has 6 public inputs:
root, nullifier_hash, recipient, recipient_binding, amount, total_amount.

Private input

Section titled “Private input”

A value known only to the prover and hidden from the verifier.
Declared in Noir without the pub keyword.

The withdrawal circuit has 7 private inputs:
nullifier, secret, note_secret, merkle_proof, is_even, splits, note_index.

Witness

Section titled “Witness”

The full set of circuit input and intermediate values (both public and private) substituted into the constraints.
Without a valid witness, a proof cannot be generated.

Constraint

Section titled “Constraint”

An algebraic equation over a finite field that circuit variables must satisfy.
If any constraint is violated, a valid proof cannot be constructed.

The withdrawal circuit enforces 5 logical constraints:

  • C1: hash_1(nullifier) == nullifier_hash
  • C2: hash_2(note_secret, recipient) == recipient_binding
  • C3: compute_merkle_root(hash_3(nullifier, secret, amount), merkle_proof, is_even) == root
  • C4: splits[0] + splits[1] + splits[2] == total_amount
  • C5: splits[note_index] == amount (subject to note_index < 3)

Prover

Section titled “Prover”

The party that computes the witness and generates the ZK proof.
In this project, this role is handled by services/prover built on Rust and Sunspot.

Verifier

Section titled “Verifier”

The party that checks proof validity against public inputs.
In this project, this is a standalone on-chain Solana program based on gnark-solana.

Commitment

Section titled “Commitment”

A cryptographic hash that binds the parameters of a deposit note without revealing them:

The original numbers cannot be recovered from the commitment, yet the owner of the secrets can prove their inclusion in the Merkle tree.

Nullifier

Section titled “Nullifier”

A secret number uniquely tied to a specific deposit note and used to prevent double-spending.
Stored strictly on the client side.

Nullifier hash

Section titled “Nullifier hash”

A public hash of the nullifier (nullifier_hash = hash_1(nullifier)) submitted on-chain during withdrawal.
Used as a seed for the NullifierRecord PDA account and as the unique identifier of a spent note in the database.

2. Hash Functions and Data Structures

Section titled “2. Hash Functions and Data Structures”

Hash function

Section titled “Hash function”

A deterministic one-way function that maps input data to a fixed-size number.
Resistant to preimage and collision attacks.

Poseidon2

Section titled “Poseidon2”

An algebraic hash function designed specifically for ZK circuits (specification: Poseidon2 paper).
Operates directly on finite field elements via additions and multiplications, requiring an order of magnitude fewer constraints than SHA-256 or Keccak.

Invoked in Noir through the built-in poseidon2_permutation function with state width t = 4.

Permutation

Section titled “Permutation”

An invertible mixing function over a fixed-size state.
In Poseidon2, applied to an array of 4 field elements (t = 4).

Rate and capacity

Section titled “Rate and capacity”

Parameters of a sponge hashing construction with state width t = r + c = 4:

  • Rate (r = 3) — number of state slots used for absorbing input data.
  • Capacity (c = 1) — reserved slot providing cryptographic collision resistance.

Because r = 3, the project defines hash_1, hash_2, and hash_3, while hash_4 is intentionally forbidden.

Zero-padding

Section titled “Zero-padding”

Filling unused rate slots with zeros:

  • hash_1(x) → state [x, 0, 0, 0]
  • hash_2(x, y) → state [x, y, 0, 0]
  • hash_3(x, y, z) → state [x, y, z, 0]

BN254

Section titled “BN254”

The elliptic curve used in Groth16, Noir, and Solana’s alt_bn128 precompiles (curve parameters: BN254 curve).
Scalar field modulus:

Values of type Field in Noir range from 0 to p - 1 (less than 2^254).
Since a 32-byte Solana public key (256 bits) can exceed the field modulus, it is reduced modulo p before entering the circuit.

Merkle tree

Section titled “Merkle tree”

A binary hash tree where leaves hold deposit commitments and each parent node equals hash_2(left, right).
Modifying any leaf changes the tree’s root hash.

The project’s tree depth is 20 (up to 2^20 = 1,048,576 leaves).

Merkle proof

Section titled “Merkle proof”

A path of 20 sibling hashes from a target leaf to the tree root, proving leaf inclusion without revealing its position.

Merkle root

Section titled “Merkle root”

The root hash of the Merkle tree compactly representing the entire deposit set.
The on-chain program maintains a ring buffer of the 10 most recent roots (ROOT_HISTORY_SIZE = 10) so concurrent deposits do not invalidate proofs already in flight.

is_even (side flag)

Section titled “is_even (side flag)”

An array of 20 boolean flags for each level of the Merkle tree:
true indicates the current node is a left child (hash_2(current, sibling)), while false indicates a right child (hash_2(sibling, current)).
Required because hash_2 is non-commutative.

3. Noir and ZK Circuits

Section titled “3. Noir and ZK Circuits”

Noir

Section titled “Noir”

A domain-specific programming language for writing ZK circuits with Rust-like syntax (documentation: Noir Documentation).
Compiles to the ACIR intermediate representation.

Nargo

Section titled “Nargo”

The command-line tool and package manager for Noir (analogous to Cargo in Rust, guide: Nargo CLI Reference).
Core commands: nargo test, nargo compile, nargo execute.

ACIR (Abstract Circuit Intermediate Representation)

Section titled “ACIR (Abstract Circuit Intermediate Representation)”

The intermediate representation of a ZK circuit produced after compiling Noir source code via nargo compile (stored in JSON files withdrawal.json, hash2.json, hashes.json).

ACIR components:

  • Input and output descriptors: indices of public and private circuit signals.
  • Constraints: mathematical equations over a finite field (arithmetic gates and built-in primitive calls such as Poseidon2) that circuit variables must satisfy.
  • Witness generation bytecode: instructions for computing all intermediate variables from given inputs.

Role of ACIR in zkpool-mesh:

  • Browser and Node.js execution: via @noir-lang/noir_js, the frontend and Merkle tree service compute Poseidon2 hashes from hash2.json, eliminating hash drift between JavaScript and Noir.
  • Server-side witness generation: nargo execute uses withdrawal.json and inputs from Prover.toml to compute the witness (withdrawal.gz).
  • Lowering to a constraint system: sunspot compile converts withdrawal.json into a low-level CCS constraint system (withdrawal.ccs) for Groth16 key and proof generation.

Nargo.toml and main.nr

Section titled “Nargo.toml and main.nr”

The Noir package manifest (Nargo.toml, specifying package type bin or lib and dependencies) and the circuit entrypoint source file (main.nr containing the main function).

Field

Section titled “Field”

The primitive numeric type in Noir representing an element of the BN254 scalar field.
Arithmetic is performed modulo the prime p.

Const generics

Section titled “Const generics”

Parameterizing functions and arrays with compile-time constants (such as compute_merkle_root), enabling code reuse across trees of varying depths.

4. Groth16 and Sunspot

Section titled “4. Groth16 and Sunspot”

Groth16

Section titled “Groth16”

A non-interactive zero-knowledge proof system (zk-SNARK, paper: Groth16 paper) featuring a constant small proof size and fast verification, making it practical to verify inside Solana transactions.

Trusted setup and MPC ceremony

Section titled “Trusted setup and MPC ceremony”

One-time generation of the proving key and verifying key for a specific circuit.
Intermediate secret parameters (toxic waste) are produced during this process.
In local and demo environments, setup runs locally; production deployments require a multi-party computation (MPC) ceremony so no single participant knows the toxic waste.

CCS (Constraint System)

Section titled “CCS (Constraint System)”

A low-level representation of the constraint system (withdrawal.ccs) derived from ACIR prior to Groth16 key generation.

Proving key (.pk) and Verifying key (.vk)

Section titled “Proving key (.pk) and Verifying key (.vk)”
  • Proving key (withdrawal.pk) — key used by the prover service to generate proofs.
  • Verifying key (withdrawal.vk) — compact public verification key embedded into the on-chain verifier program.

Sunspot

Section titled “Sunspot”

An open-source toolkit by Reilabs (repository: reilabs/sunspot) bridging the Noir compiler with Solana via the gnark proving backend and the gnark-solana Rust verifier.

Architectural role of Sunspot in zkpool-mesh:

  • Lowering ACIR to R1CS/CCS (sunspot compile):
    converts the intermediate representation withdrawal.json into a Groth16 constraint system (withdrawal.ccs).
  • Key generation (sunspot setup):
    generates the proving key (withdrawal.pk) and verifying key (withdrawal.vk) for the target circuit.
  • Building the on-chain verifier (sunspot deploy):
    compiles the gnark-solana/crates/verifier-bin Rust crate for Solana BPF (via cargo build-sbf), embedding withdrawal.vk directly into the withdrawal.so program binary, which uses Solana’s alt_bn128 syscalls to verify BN254 elliptic curve pairings.
  • Proof generation and verification (sunspot prove / sunspot verify):
    takes the compiled circuit, the witness from nargo execute (withdrawal.gz), and the proving key to produce a binary Groth16 proof (withdrawal.proof, 388 bytes) and public witness (withdrawal.pw, 204 bytes).

Proof (.proof) and Public witness (.pw)

Section titled “Proof (.proof) and Public witness (.pw)”
  • Proof — binary Groth16 proof (388 bytes in the current project configuration).
  • Public witness — serialized public inputs (204 bytes: 12-byte header plus six 32-byte fields) passed to the verifier alongside the proof.

5. Solana and On-Chain Architecture

Section titled “5. Solana and On-Chain Architecture”

Program, BPF, and Platform Tools

Section titled “Program, BPF, and Platform Tools”

A smart contract on Solana is called a program, stored in an executable account as BPF (Berkeley Packet Filter) bytecode and compiled from Rust with cargo build-sbf using Solana Platform Tools v1.58 (documentation: Solana Programs).
Two programs are deployed in the project: zk_pool and verifier.

Solana CLI / Agave

Section titled “Solana CLI / Agave”

The Solana command-line client toolchain (Agave validator client, version v4.4.1) and local test validator solana-test-validator, used to deploy programs and submit transactions over HTTP RPC.

Program ID and ProgramData

Section titled “Program ID and ProgramData”

Program ID — immutable public address of a program.
The executable bytecode of an upgradeable program is stored in a separate linked ProgramData account, allowing logic upgrades without changing the program address (while upgrade authority remains active).

Rent

Section titled “Rent”

The minimum lamport balance required to keep account data stored on-chain (rent-exempt, details: Solana Accounts & Rent).

PDA (Program Derived Address)

Section titled “PDA (Program Derived Address)”

A deterministic account address with no private key, derived from a set of text or binary seeds and a Program ID (documentation: Program Derived Addresses).
Only the owning program can sign operations on behalf of a PDA.

zk_pool uses three PDA types:

  • pool — seeds: [“pool3”]
  • vault — seeds: [“vault3”, pool]
  • nullifier_record — seeds: [“nullifier_record”, pool, nullifier_hash]

CPI (Cross-Program Invocation)

Section titled “CPI (Cross-Program Invocation)”

Inter-program invocation on Solana (documentation: Cross-Program Invocation).
The withdraw instruction of zk_pool invokes the verifier program via CPI to validate the Groth16 proof.

Transaction, Instruction, and Discriminator

Section titled “Transaction, Instruction, and Discriminator”

A transaction bundles one or more atomic instructions.
Every Anchor instruction begins with an 8-byte discriminator — a SHA-256 prefix of the instruction name used by the program to route execution.

Anchor and IDL

Section titled “Anchor and IDL”

A Rust framework for building Solana programs (documentation: Anchor Framework, version v1.2.2).
Automatically generates a JSON interface specification — IDL (Interface Description Language) — used by clients and tests to construct instructions.

6. Project Domain Terms

Section titled “6. Project Domain Terms”

Deposit note

Section titled “Deposit note”

A bundle of secret parameters (nullifier, secret, note_secret, amount, commitment) enabling withdrawal of the corresponding deposit share.
When deposit_split is called, the deposit amount is split into three parts (SPLIT_COUNT = 3), three commitments are inserted into the Merkle tree, and the user receives three independent notes for partial withdrawals.

Pool and Vault

Section titled “Pool and Vault”
  • Pool — pool state account (PDA [“pool3”]) storing the Merkle tree root, history of the last 10 roots, and leaf counter.
  • Vault — system custody account (PDA [“vault3”, pool]) holding deposited SOL. Separating state from custody prevents mixing account data with transferable funds.

Recipient_binding and front-running protection

Section titled “Recipient_binding and front-running protection”

Front-running — intercepting a valid transaction in the mempool and broadcasting a copy with a substituted recipient address and higher priority fee.
The field recipient_binding = hash_2(note_secret, recipient) cryptographically binds the proof to a specific recipient address: substituting recipient violates constraint C2 and causes the transaction to fail.

Double-spend

Section titled “Double-spend”

An attempt to withdraw the same deposit note more than once.
Prevented by creating a nullifier_record PDA account on the first withdrawal:
any subsequent transaction reusing the same nullifier_hash fails at the Solana runtime level.

spec.json and validate-spec

Section titled “spec.json and validate-spec”

spec.json (circuits/withdrawal/spec.json) — single source of truth defining public and private inputs, array dimensions, and public witness byte layout.
The validate-spec CLI checks 17 internal consistency rules before building services.

sync-circuits

Section titled “sync-circuits”

A Rust CLI tool (scripts/sync-circuits/) that synchronizes compiled ACIR files from circuits/ to consumer services (services/merkle/circuits/ and web/public/circuits/).
In check mode, it runs in CI to block artifact drift using SHA-256 checksums.

7. Backend, Microservices, and Frontend

Section titled “7. Backend, Microservices, and Frontend”

Rust, Cargo, and Axum

Section titled “Rust, Cargo, and Axum”

Primary language (Rust, version 1.100.0) and build system for the on-chain zk_pool program, backend indexer, prover service, CLI utilities, and tests.
The Axum web framework (v0.7) on top of the Tokio async runtime serves HTTP APIs for backend (:4001) and prover (:4002).

Indexer

Section titled “Indexer”

A background component of the backend service that polls Solana RPC for PROGRAM_ID events, decodes deposit logs, and persists commitments and Merkle roots to PostgreSQL and Redis.

Node.js, pnpm, and Fastify

Section titled “Node.js, pnpm, and Fastify”

The Node.js runtime (v26.13.1), pnpm package manager (v12.21.0), and Fastify web framework (v5.12.5) powering the Merkle tree service (services/merkle, port :4003).

@noir-lang/noir_js

Section titled “@noir-lang/noir_js”

JavaScript/WASM execution library for compiled Noir circuits (documentation: NoirJS).
Used in the Merkle tree service to compute Poseidon2 hashes and in the frontend for in-browser witness generation.

PostgreSQL 16 and Redis 7

Section titled “PostgreSQL 16 and Redis 7”
  • PostgreSQL 16 — relational database for persistent storage of indexed commitments and Merkle root history.
  • Redis 7 — in-memory store caching the current Merkle tree size and root.

Vue 3, Vite, Pinia, TypeScript, Pug, SCSS, and @solana/kit

Section titled “Vue 3, Vite, Pinia, TypeScript, Pug, SCSS, and @solana/kit”

Frontend technology stack (web/):

  • Vue 3 reactive UI framework,
  • Vite build tool,
  • Pinia state store,
  • strict TypeScript typing,
  • Pug template engine,
  • SCSS stylesheet preprocessor, and modular @solana/kit SDK for wallet and Solana RPC interactions.

API Gateway and Contract Testing

Section titled “API Gateway and Contract Testing”

Single entry point for request routing and rate limiting across microservices (backend, merkle, prover), paired with contract testing of request/response schemas between API consumers and providers.

Playwright

Section titled “Playwright”

End-to-end (E2E) browser testing framework (documentation: Playwright) verifying wallet connection, deposit, and withdrawal user flows in a real browser.

8. Build, Infrastructure, and Orchestration

Section titled “8. Build, Infrastructure, and Orchestration”

Modular boot.sh and cache warming (cache/)

Section titled “Modular boot.sh and cache warming (cache/)”

Environment bootstrap script (scripts/boot.sh and modules scripts/boot/common.sh, toolchain.sh, deps.sh, env.sh) that pre-downloads compilers (Go 1.27.4, Rust, Solana, Anchor, Node.js, pnpm, Nargo, Sunspot), Cargo dependencies (cache/cargo-registry/, cache/cargo-git/), pnpm packages (cache/pnpm-store/), and base Docker images (cache/images/*.tar).

pin-versions.sh and switch-network.sh

Section titled “pin-versions.sh and switch-network.sh”
  • pin-versions.sh — script that automatically records actual tool versions from built containers into .env.
  • switch-network.sh — script that synchronously switches project configuration between the local validator (localnet) and public testnet (devnet).

Docker, Compose, and modular Makefile

Section titled “Docker, Compose, and modular Makefile”

Containerized environment (Docker Engine & Compose) split across four specialized images and containers:

  • zkpool-mesh (backend, prover, contract and circuit builds),
  • zkpool-merkle (Merkle tree service),
  • zkpool-web (nginx frontend),
  • zkpool-validator (local Solana validator). Lifecycle management is organized into modules
    infra/mk/infra.mk, chain.mk, stack.mk, test.mk, diag.mk.

Terraform and Ansible

Section titled “Terraform and Ansible”

Infrastructure as Code (Terraform) and configuration management (Ansible) tools for automated provisioning of cloud infrastructure (Oracle Cloud Always Free ARM) and initial cluster node setup.

K3s, Helm, Ingress, and Sealed Secrets

Section titled “K3s, Helm, Ingress, and Sealed Secrets”

Lightweight Kubernetes distribution (K3s), deployment package templating (Helm), external traffic routing controller (Ingress), and encrypted secret storage in Git (Bitnami Sealed Secrets).

9. DevSecOps and Observability

Section titled “9. DevSecOps and Observability”

SAST and CodeQL

Section titled “SAST and CodeQL”

Static Application Security Testing via GitHub CodeQL to automatically detect vulnerabilities in Rust, TypeScript, and JavaScript prior to merging changes.

Trivy, cargo-deny, and cargo-audit

Section titled “Trivy, cargo-deny, and cargo-audit”

Dependency and container image vulnerability scanners:
Trivy scans Docker images and filesystems, while cargo-deny and cargo-audit enforce license policies and check for known CVEs in Rust crates.

Gitleaks

Section titled “Gitleaks”

Automated scanner for detecting accidentally committed private keys, tokens, and secrets in Git history (documentation: Gitleaks).

SBOM, Syft, and Cosign

Section titled “SBOM, Syft, and Cosign”
  • SBOM (Software Bill of Materials) — machine-readable inventory of all build components and dependencies generated by Syft.
  • Cosign — cryptographic signing tool for container images and artifacts to guarantee supply-chain integrity.

GitOps and Argo CD

Section titled “GitOps and Argo CD”

Declarative Kubernetes deployment practice where the Git repository serves as the single source of cluster state and the Argo CD controller automatically reconciles changes.

Prometheus, Grafana, Loki, Tempo, and Alertmanager

Section titled “Prometheus, Grafana, Loki, Tempo, and Alertmanager”

Full observability stack:

  • Prometheus — numerical service metrics collection.
  • Loki — centralized container log aggregation and search.
  • Tempo — distributed tracing for cross-service requests.
  • Alertmanager — alert routing when alerting rules fire.
  • Grafana — unified visualization interface for metrics, logs, and traces.

SLO (Service Level Objective)

Section titled “SLO (Service Level Objective)”

Target service reliability metrics (API latency, transaction success rate, and service availability) used to track system health.

SHA-256 and checkpoints

Section titled “SHA-256 and checkpoints”

The SHA-256 cryptographic hash function is used for byte-level integrity verification of compiled ACIR circuits (sync-circuits) and recording artifact checkpoints (.checkpoints/).
