Glossary

Reference dictionary of terms used across the zkpool-mesh project.
Terms are grouped by domain and defined without jargon.

1. Zero-Knowledge Cryptography (ZK)

Section titled “1. Zero-Knowledge Cryptography (ZK)”

ZK proof

Section titled “ZK proof”

A cryptographic method for proving knowledge of a secret without revealing the secret itself.

In zkpool-mesh, a user proves ownership of the secrets behind one of the deposit notes in the pool without revealing which note it is.
This breaks the on-chain link between the deposit transaction and withdrawal transactions.

Circuit

Section titled “Circuit”

A program describing the statement being proven.
It consists of public inputs, private inputs, and a set of mathematical constraints.

The project uses the withdrawal circuit, which enforces five logical statements (C1–C5).

Public input

Section titled “Public input”

A value known to both the prover and the verifier.
Declared in Noir with the pub keyword.

The withdrawal circuit defines 6 public inputs:
root, nullifier_hash, recipient, recipient_binding, amount, total_amount.

Private input

Section titled “Private input”

A value known only to the prover and hidden from the verifier.
Declared in Noir without pub.

The withdrawal circuit defines 7 private inputs:
nullifier, secret, note_secret, merkle_proof, is_even, splits, note_index.

Witness

Section titled “Witness”

The complete set of input values (both public and private) substituted into the circuit constraints.
Generating a proof is impossible without a valid witness.

Constraint

Section titled “Constraint”

An algebraic equation that circuit inputs must satisfy.
If even a single constraint fails, no valid proof can be constructed.

The withdrawal circuit enforces 5 logical constraints:

  • C1: hash_1(nullifier) == nullifier_hash.
  • C2: hash_2(note_secret, recipient) == recipient_binding.
  • C3: compute_merkle_root(hash_3(nullifier, secret, amount), merkle_proof, is_even) == root.
  • C4: splits[0] + splits[1] + splits[2] == total_amount.
  • C5: splits[note_index] == amount (with note_index < 3).

Prover

Section titled “Prover”

The party that computes the witness and generates the ZK proof.
In this project, this role is handled by services/prover built on Rust and Sunspot.

Verifier

Section titled “Verifier”

The party that checks proof validity against public inputs.
In this project, it is a standalone on-chain Solana program (gnark-solana).

Commitment

Section titled “Commitment”

A cryptographic hash binding deposit note parameters without revealing them:

The underlying numbers cannot be recovered from a commitment, yet the holder of the secrets can prove they correspond to a leaf in the Merkle tree.

Nullifier

Section titled “Nullifier”

A secret number uniquely tied to a specific deposit note and used to prevent double-spending.
Stored exclusively on the user side.

Nullifier hash

Section titled “Nullifier hash”

The public hash of a nullifier (nullifier_hash = hash_1(nullifier)), published on-chain during withdrawal.
Used as a PDA seed for NullifierRecord and as the spent-note key in the backend database.

2. Hash Functions and Data Structures

Section titled “2. Hash Functions and Data Structures”

Hash function

Section titled “Hash function”

A deterministic one-way function mapping arbitrary-length input data to a fixed-size number, resistant to preimage and collision attacks.

Poseidon2

Section titled “Poseidon2”

An algebraic hash function designed specifically for ZK circuits.
It operates directly on finite-field elements using additions and multiplications, requiring an order of magnitude fewer constraints than SHA-256 or Keccak.

Invoked in Noir via the built-in poseidon2_permutation with state width t = 4.

Permutation

Section titled “Permutation”

An invertible mixing function over a fixed-size state.
In Poseidon2, it operates on an array of 4 field elements (t = 4).

Rate and capacity

Section titled “Rate and capacity”

Parameters of a sponge hash construction with state width t = r + c = 4:

  • Rate (r = 3) — number of state slots used to absorb input elements.
  • Capacity (c = 1) — reserved slot providing cryptographic collision resistance.

Because r = 3, the project defines hash_1, hash_2, and hash_3, and intentionally omits hash_4.

Zero-padding

Section titled “Zero-padding”

Filling unused rate slots with zeros:

  • hash_1(x) → state [x, 0, 0, 0]
  • hash_2(x, y) → state [x, y, 0, 0]
  • hash_3(x, y, z) → state [x, y, z, 0]

BN254

Section titled “BN254”

The elliptic curve used by Groth16, Noir, and Solana precompiles (alt_bn128).
Scalar field modulus:

Values of type Field in Noir range from 0 to p - 1 (roughly 2^254).
Since a 32-byte Solana public key (256 bits) can exceed the field modulus, it is reduced modulo p before entering the circuit.

Merkle tree

Section titled “Merkle tree”

A binary hash tree where leaves store deposit commitments and each parent node equals hash_2(left, right).
Modifying any leaf changes the root hash.

The tree depth in this project is 20 (up to 2^20 = 1,048,576 leaves).

Merkle proof

Section titled “Merkle proof”

A path of 20 sibling hashes from a target leaf up to the tree root, proving leaf inclusion without revealing its index.

Merkle root

Section titled “Merkle root”

The root hash of the Merkle tree compactly representing the entire set of deposits.
The on-chain program maintains a ring buffer of the last 10 roots (ROOT_HISTORY_SIZE = 10) so concurrent deposits do not invalidate proofs already in flight.

is_even (side flag)

Section titled “is_even (side flag)”

An array of 20 boolean flags, one per Merkle tree level: true indicates the current node is the left child (hash_2(current, sibling)), while false indicates the right child (hash_2(sibling, current)). Required because hash_2 is non-commutative.

3. Noir and ZK Circuits

Section titled “3. Noir and ZK Circuits”

Noir

Section titled “Noir”

A domain-specific programming language for writing ZK circuits with Rust-like syntax.
Compiles to the ACIR intermediate representation.

Nargo

Section titled “Nargo”

The command-line toolchain and package manager for Noir (analogous to Cargo in Rust).
Core commands: nargo test, nargo compile, nargo execute.

ACIR (Abstract Circuit Intermediate Representation)

Section titled “ACIR (Abstract Circuit Intermediate Representation)”

A platform-independent intermediate representation of a compiled circuit containing input definitions, constraints, and witness-generation bytecode.
Stored in JSON files (such as withdrawal.json).

Nargo.toml and main.nr

Section titled “Nargo.toml and main.nr”

The Noir package manifest (Nargo.toml, defining package type bin or lib and dependencies) and the circuit entry-point source file (main.nr containing main).

Field

Section titled “Field”

The primitive numeric type in Noir representing an element of the BN254 scalar field. Arithmetic is performed modulo the prime p.

Const generics

Section titled “Const generics”

Parameterizing functions and arrays with compile-time constants (such as compute_merkle_root), enabling code reuse across trees of different depths.

4. Groth16 and Sunspot

Section titled “4. Groth16 and Sunspot”

Groth16

Section titled “Groth16”

A zero-knowledge succinct non-interactive argument of knowledge (zk-SNARK) featuring constant small proof size and fast verification, making it suitable for verification inside Solana transactions.

Trusted setup and MPC ceremony

Section titled “Trusted setup and MPC ceremony”

A one-time procedure generating the proving key and verifying key for a circuit. The process produces intermediate secret parameters (toxic waste). In a demo environment, setup runs locally; production deployments require a multi-party computation (MPC) ceremony so no single participant knows the toxic waste.

CCS (Constraint System)

Section titled “CCS (Constraint System)”

A low-level representation of the constraint system (withdrawal.ccs) compiled from ACIR prior to Groth16 key generation.

Proving key (.pk) and Verifying key (.vk)

Section titled “Proving key (.pk) and Verifying key (.vk)”
  • Proving key (withdrawal.pk) — key used by the prover service to generate proofs.
  • Verifying key (withdrawal.vk) — compact public verification key embedded into the on-chain verifier program.

Sunspot

Section titled “Sunspot”

A toolchain bridging Noir and Solana (built on gnark-solana). Handles ACIR-to-CCS compilation (sunspot compile), key generation (sunspot setup), on-chain verifier build and deployment (sunspot deploy), and proof generation (sunspot prove).

Proof (.proof) and Public witness (.pw)

Section titled “Proof (.proof) and Public witness (.pw)”
  • Proof — binary Groth16 proof (388 bytes in the current project configuration).
  • Public witness — serialized public inputs (204 bytes: a 12-byte header plus six 32-byte field elements) passed alongside the proof to the verifier.

5. Solana

Section titled “5. Solana”

Program and BPF

Section titled “Program and BPF”

A smart contract on Solana is called a program, stored in an executable account as BPF (Berkeley Packet Filter) bytecode compiled from Rust via cargo build-sbf. Two programs are used: zk_pool and verifier.

Program ID and ProgramData

Section titled “Program ID and ProgramData”

Program ID is the immutable public address of a program. Upgradeable program bytecode is stored in a linked ProgramData account, allowing logic updates without changing the program address while upgrade authority remains active.

Rent

Section titled “Rent”

The minimum lamport balance required to keep an account stored on-chain (rent-exempt).

PDA (Program Derived Address)

Section titled “PDA (Program Derived Address)”

A deterministic account address with no private key, derived from seeds and a Program ID. Only the owning program can sign for its PDAs.

zk_pool uses three PDA types:

  • pool — seeds: [“pool3”].
  • vault — seeds: [“vault3”, pool].
  • nullifier_record — seeds: [“nullifier_record”, pool, nullifier_hash].

CPI (Cross-Program Invocation)

Section titled “CPI (Cross-Program Invocation)”

A direct call from one Solana program to another. The withdraw instruction in zk_pool invokes the verifier program via CPI to validate the Groth16 proof.

Transaction, Instruction, and Discriminator

Section titled “Transaction, Instruction, and Discriminator”

A transaction bundles one or more atomic instructions. Every Anchor instruction begins with an 8-byte discriminator — a SHA-256 prefix of the instruction name used for routing.

6. Project Domain Terms

Section titled “6. Project Domain Terms”

Deposit note

Section titled “Deposit note”

A bundle of secret parameters (nullifier, secret, note_secret, amount, commitment) required to withdraw a corresponding deposit portion. Calling deposit_split splits a deposit into three parts (SPLIT_COUNT = 3), inserts three commitments into the Merkle tree, and issues three independent notes so funds can be withdrawn in separate portions.

Pool and Vault

Section titled “Pool and Vault”

• Pool — pool state account (PDA [“pool3”]) storing the Merkle root, a history of the last 10 roots, and the leaf counter. • Vault — system-owned escrow account (PDA [“vault3”, pool]) holding deposited SOL. Separating state from SOL balance prevents account data from mixing with custodied funds.

recipient_binding and front-running protection

Section titled “recipient_binding and front-running protection”

Front-running is an attack where an observer intercepts a pending transaction in the mempool and submits a copy with a substituted recipient address and higher priority fee. The field recipient_binding = hash_2(note_secret, recipient) cryptographically binds the proof to a specific recipient address: substituting recipient violates constraint C2 and rejects the transaction.

Double-spend

Section titled “Double-spend”

An attempt to withdraw the same deposit note more than once. Prevented by creating a nullifier_record PDA on the first withdrawal: any subsequent transaction with the same nullifier_hash fails at the Solana runtime level.

spec.json and validate-spec

Section titled “spec.json and validate-spec”

spec.json (circuits/withdrawal/spec.json) is the single source of truth defining public inputs, private inputs, array dimensions, and public witness layout. The validate-spec CLI verifies internal consistency before services are built.

sync-circuits

Section titled “sync-circuits”

A Rust CLI (scripts/sync-circuits/) that syncs compiled ACIR files from circuits/ into consumer services (services/merkle/circuits/ and web/public/circuits/). Its –check mode fails CI whenever artifacts drift out of sync.

7. Development Tools

Section titled “7. Development Tools”

Rust and Cargo

Section titled “Rust and Cargo”

Primary language and build system for the zk_pool on-chain program, backend, prover service, CLI utilities, and LiteSVM integration tests.

Anchor and IDL

Section titled “Anchor and IDL”

A Rust framework for Solana programs. Automatically generates an IDL (Interface Description Language) JSON specification used by clients and tests to construct instructions.

@solana/kit

Section titled “@solana/kit”

A modular TypeScript SDK used in the frontend for Solana RPC communication, transaction building, and address handling.

Node.js, pnpm, Vite, Vue 3, Pinia

Section titled “Node.js, pnpm, Vite, Vue 3, Pinia”

• Node.js 24 and pnpm 12 — runtime and package manager for the merkle service and frontend. • Vite, Vue 3, and Pinia — bundler, reactive UI framework, and state manager for the web application.

@noir-lang/noir_js

Section titled “@noir-lang/noir_js”

A JavaScript/WASM execution runtime for compiled Noir circuits. Used in the merkle service to compute Poseidon2 hashes and in the frontend to generate witnesses in the browser.

Docker and Compose

Section titled “Docker and Compose”

Container environment split into four purpose-built images and containers: zkpool-mesh (backend, prover, contract and circuit builds), zkpool-merkle (Merkle tree service), zkpool-web (nginx frontend), and zkpool-validator (local Solana test validator).

Prometheus and Grafana

Section titled “Prometheus and Grafana”

Observability stack: Prometheus scrapes service metrics, and Grafana renders monitoring dashboards.

SHA-256

Section titled “SHA-256”

Cryptographic hash function used by the checkpoint system (.checkpoints/) to enforce byte-level artifact consistency across development stages.
