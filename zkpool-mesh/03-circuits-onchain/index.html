Stage 2: Noir ZK Circuits and the Sunspot Pipeline

Stage 2 establishes the cryptographic core of zkpool-mesh:

  • zero-knowledge proof circuits written in Noir,
  • a single source-of-truth contract for public and private inputs in spec.json,
  • the Sunspot pipeline that compiles ACIR intermediate representations into an on-chain Groth16 verifier program for Solana.

1. Why Noir and Poseidon2

Section titled “1. Why Noir and Poseidon2”

Choosing the Noir + Sunspot stack solves two core requirements of a privacy pool on Solana:

  • Single ACIR across browser, Node.js, and Rust:
    compiled circuit artifacts (hash2.json, hashes.json, withdrawal.json) execute in the browser and the Merkle tree service via @noir-lang/noir_js, and on the prover server via nargo execute and sunspot prove.
    This prevents hash mismatches across programming languages.
  • Poseidon2 arithmetic over the BN254 curve:
    bitwise hash functions such as SHA-256 require hundreds of constraints per invocation inside an arithmetic circuit.
    Poseidon2 operates natively over the BN254 scalar field with state parameters t = 4, rate = 3, capacity = 1, reducing constraint counts and proving times by orders of magnitude.
  • Groth16 compactness for Solana transactions:
    Solana transaction size is capped at 1,232 bytes.
    The Groth16 proving system (implemented in Sunspot on top of gnark-solana) produces a fixed 388-byte proof and fast on-chain verification via alt_bn128 precompiles.

2. Single Source of Truth: circuits/withdrawal/spec.json

Section titled “2. Single Source of Truth: circuits/withdrawal/spec.json”

The file circuits/withdrawal/spec.json defines the circuit interface as structured data:

  • Circuit parameters:
    • name withdrawal,
    • entrypoint main,
    • Merkle tree depth tree_depth = 20,
    • split deposit support split_count = 3,
    • public input count nr_public_inputs = 6.
  • 6 public inputs (192 bytes in the witness section):
    1. root (field, 32 bytes, BN254 big-endian) — current or historical Merkle root from the pool’s ring buffer.
    2. nullifier_hash (field, 32 bytes) — hash_1(nullifier), used as the PDA seed for the spent nullifier record.
    3. recipient (pubkey, 32 bytes) — Solana recipient public key reduced modulo the BN254 field prime.
    4. recipient_binding (field, 32 bytes) — hash_2(note_secret, recipient), binding the proof to a specific recipient and preventing front-running.
    5. amount (u64, 8 bytes, right-aligned in a 32-byte word) — withdrawal amount for the current note in lamports.
    6. total_amount (u64, 8 bytes, right-aligned in a 32-byte word) — aggregate deposit amount across all three split notes.
  • 7 private inputs:
    1. nullifier,
    2. secret,
    3. note_secret,
    4. sibling hash array merkle_proof,
    5. path direction flag array is_even,
    6. deposit split vector splits,
    7. current note index note_index (u32).
  • 5 circuit constraints (C1–C5):
    1. C1: hash_1(nullifier) == nullifier_hash
    2. C2: hash_2(note_secret, recipient) == recipient_binding
    3. C3: compute_merkle_root(hash_3(nullifier, secret, amount), merkle_proof, is_even) == root
    4. C4: splits + splits + splits == total_amount
    5. C5: splits[note_index] == amount (after asserting note_index < 3)
  • Witness header and buffer layout (204 bytes): 12-byte header (nr_public_inputs as u32 BE, reserved zero u32 BE, repeated nr_public_inputs as u32 BE) + 6 × 32 = 192 bytes of public inputs.

3. Specification Validation (scripts/validate-spec)

Section titled “3. Specification Validation (scripts/validate-spec)”

To automatically verify internal consistency of spec.json, the Rust CLI scripts/validate-spec (target make validate-spec) enforces 17 validation rules:

The validator checks the schema version, tree depth (20), split dimensionality (3), unique public input names, raw byte sum (144) and witness slot sum (192), total buffer size (204 bytes), all five constraints (C1–C5), prohibition of hash_4 (which would zero out the Poseidon2 permutation capacity), and the list of artifact consumers (prover, merkle, web).

4. Four Noir Packages (circuits/)

Section titled “4. Four Noir Packages (circuits/)”

The circuit codebase is split into a shared library and three executable packages:

  1. circuits/poseidon (type = “lib”):
    implements hash_1, hash_2, and hash_3 on top of std::hash::poseidon2_permutation with zero-padding to 4 elements.
    The hash_4 function is intentionally forbidden to preserve a non-zero capacity slot.
    Covered by 11 unit tests (determinism, non-commutativity, and documented zero-padding properties).
  2. circuits/hash2 (type = “bin”):
    wrapper around hash_2(left, right) -> pub Field.
    Compiles to hash2.json for computing Merkle tree nodes in services/merkle and the frontend (5 tests).
  3. circuits/hashes (type = “bin”):
    computes the pair (commitment, nullifier_hash) from (nullifier, secret, amount) to verify note parameters before submitting a deposit (9 tests).
  4. circuits/withdrawal (type = “bin”):
    the main withdrawal circuit with modules merkle_tree.nr (20-level leaf-to-root traversal using direction flags is_even[i]) and test_witness.nr (reference witness generator).
    Covered by 24 tests verifying constraints C1–C5, out-of-bounds note_index rejection, and full tree traversal.

5. ACIR Artifact Synchronization (scripts/sync-circuits)

Section titled “5. ACIR Artifact Synchronization (scripts/sync-circuits)”

After circuit compilation (nargo compile), binary ACIR JSON files must remain identical across every system component:

The scripts/sync-circuits CLI supports two modes:

  • make sync (sync-circuits apply) — compiles hash2, hashes, and withdrawal, computes their SHA-256 hashes, and copies up-to-date artifacts to services/merkle/circuits/ and web/public/circuits/.
  • make sync-check (sync-circuits check) — read-only CI mode that exits with code 1 if any consumer copy diverges from the source ACIR hash.

6. Sunspot Pipeline: From ACIR to On-Chain Verifier

Section titled “6. Sunspot Pipeline: From ACIR to On-Chain Verifier”

During make chain (module infra/mk/chain.mk), withdrawal.json passes through four Sunspot stages:

  1. sunspot compile target/withdrawal.json — lowers high-level Poseidon2 operations and the Merkle tree loop into an R1CS/CCS constraint system (target/withdrawal.ccs).
  2. sunspot setup target/withdrawal.ccs — generates the proving key (target/withdrawal.pk) and verifying key (target/withdrawal.vk). In local and test environments setup runs locally; production deployments require a multi-party computation (MPC) ceremony.
  3. sunspot deploy target/withdrawal.vk — compiles the gnark-solana verifier crate (GNARK_VERIFIER_BIN=/home/i/sunspot/gnark-solana/crates/verifier-bin) via cargo build-sbf, embedding the verifying key into the BPF binary target/withdrawal.so and creating target/withdrawal-keypair.json.
  4. solana program deploy + ID synchronization — deploys the verifier to the validator (–use-rpc), extracts the new VERIFIER_PROGRAM_ID, and automatically writes it to onchain/programs/zk_pool/src/constants.rs and .env before building zk_pool.

When handling a withdrawal request, zkpool-prover executes the reverse flow:
nargo execute generates the witness withdrawal.gz, and sunspot prove produces the 388-byte Groth16 proof (withdrawal.proof) and 204-byte public witness (withdrawal.pw), which is verified at the protocol level.

7. Pitfalls and Practical Solutions

Section titled “7. Pitfalls and Practical Solutions”
  • BN254 field overflow when passing 256-bit values:
    the BN254 scalar field prime is smaller than 2^254, so an arbitrary 32-byte Solana Pubkey cannot be passed directly into a Field. Every layer (Rust contract, zkpool-prover, and frontend) applies a consistent modulo reduction into the BN254 field.
  • Parsing large hex literals in Prover.toml:
    the TOML parser in nargo attempts to parse unquoted hex literals as 64-bit signed integers and fails on overflow. All Field values in Prover.toml must be wrapped in double quotes (“0x…”).
  • Overwriting withdrawal-keypair.json on each sunspot deploy:
    every invocation of sunspot deploy generates a fresh keypair and changes the verifier Program ID. In infra/mk/chain.mk, building the verifier strictly precedes building zk_pool, and the new VERIFIER_PROGRAM_ID is automatically injected into the Rust source and .env.
  • Deprecated ALT_BN128_ constants when building gnark-solana:*
    compiling verifier-bin emits compiler warnings about deprecated solana_bn254 constants. This comes from the upstream gnark-solana crate and does not affect .so compilation or pairing verification.
