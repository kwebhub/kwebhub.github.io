Introduction

Zkpool-mesh is a reference implementation of a zero-knowledge private pool for SOL transfers on Solana, built with microservices, K3s, and DevSecOps practices.

Demo / educational project.
Not production software.
Solana Devnet only.

Why this project exists

Section titled “Why this project exists”

Most ZK tutorials stop at a standalone circuit or a single smart contract.
Real-world privacy protocols require off-chain indexers, Merkle tree services, prover workers, a frontend witness pipeline, automated testing, infrastructure as code, and continuous security verification.

Zkpool-mesh bridges that gap by walking through the full software development lifecycle — from local circuit compilation to a GitOps-managed Kubernetes cluster.

How it works

Section titled “How it works”
  • Deposit.
    A user sends SOL into a shared on-chain vault.
    The deposit amount is split into three parts — corresponding cryptographic commitments are inserted into a Merkle tree, and the user receives three secret deposit notes.
    This allows withdrawing funds in different portions and protects against amount-based deanonymization.
  • Withdraw.
    Using a Groth16 proof (Noir on BN254), the user proves knowledge of the secrets behind one of the notes without revealing which one, and withdraws its SOL denomination to any destination address.
  • Unlinkability.
    The on-chain verifier checks the proof and records a nullifier hash to prevent double-spending, while keeping the link between deposit and withdrawals private.

Architecture

Section titled “Architecture”
  • Frontend (:8080) — Vue 3, Vite, Pinia, TypeScript, Pug, and SCSS served by nginx:alpine. Generates witness inputs in the browser.
  • Backend (:4001) — Rust (axum) API gateway, chain indexer, PostgreSQL persistence, and Redis caching.
  • Merkle Service (:4003) — Node.js (Fastify) service computing Poseidon2 hashes via @noir-lang/noir_js.
  • Prover (:4002) — Rust (axum) worker orchestrating nargo and sunspot to generate Groth16 proofs.
  • On-chain (:8899) — Solana Anchor program (zk_pool) and gnark-solana Groth16 verifier.
  • Observability (:9090/:3000) — Prometheus, Grafana, Loki, Tempo, and Alertmanager.

Introduction to ZK Proofs

Section titled “Introduction to ZK Proofs”

This primer is intended for readers with no prior background in zero-knowledge cryptography.
If concepts such as ZK-proof, commitment, nullifier, and Merkle tree are already familiar, jump directly to the implementation chapters.

The zkpool-mesh project is built end-to-end on zero-knowledge proofs: from the Noir circuit architecture to proof verification inside a Solana smart contract.
Understanding the fundamentals explains why the circuit takes 6 public and 7 private inputs, why each deposit is split into three notes, and why a proof occupies 388 bytes.

1. The Problem: Privacy on a Public Blockchain

Section titled “1. The Problem: Privacy on a Public Blockchain”

On a standard blockchain, all transactions, addresses, and amounts are visible to any observer.
Analytics engines readily construct transaction graphs linking wallets together.

If 1 SOL is sent from address A into a conventional contract and 1 SOL is later withdrawn to address B, an observer correlates the two events by amount and timing:

  • Address A funded the contract with 1 SOL.
  • Address B received 1 SOL from the contract.

The link between addresses A and B becomes obvious.

A private pool breaks this link through two mechanisms:

  • Cryptographic hiding of which specific deposit is spent during withdrawal.
  • Split deposits — upon funding the pool, the deposited sum is split into three independent notes so funds can be withdrawn in separate portions of varying denominations, preventing amount-based deanonymization.

2. The Core Idea of ZK Proofs

Section titled “2. The Core Idea of ZK Proofs”

A ZK-proof (zero-knowledge proof) is a cryptographic protocol allowing one party (Prover) to convince another party (Verifier) that a given statement is true without revealing any information beyond the validity of the statement itself.

A classic illustration is Ali Baba’s cave with two entrances (A and B) connected internally by a secret door with a combination lock:

  • The Verifier waits outside while the Prover enters the cave through one entrance.
  • The Verifier randomly picks an exit (A or B) and asks the Prover to emerge from it.
  • Knowing the secret door code, the Prover always exits through the requested side; without the code, the Prover succeeds only 50% of the time.
  • After 20 rounds, the probability of guessing by chance drops to 1 in a million, while the code itself is never spoken aloud.

In zkpool-mesh, these roles map directly to system components:

  • The secret door code — the private parameters of a deposit note (nullifier, secret, note_secret, Merkle path, splits vector, and note_index).
  • Prover — the combination of the frontend (browser application) and the prover backend service. The frontend collects secrets from local storage and assembles the full set of inputs (witness), while the prover service computes the Groth16 cryptographic proof.
  • Verifier — the on-chain verifier program on Solana (invoked by the zk_pool smart contract).
    The contract has no access to user secrets, yet mathematically verifies the proof and unlocks the vault to transfer SOL to the recipient.

3. Application to Private Transfers

Section titled “3. Application to Private Transfers”
  • Prover (frontend and proof-generation service) knows the secret parameters of a specific deposit note.
  • Verifier (on-chain Solana program) checks the mathematical proof.
  • The Verifier confirms that the note genuinely exists in the pool, has not yet been spent, and belongs to the holder of the secrets, without learning which deposit in the tree was used.

As a result, the contract transfers SOL to the designated address while the link between deposit and withdrawal remains hidden.

4. Circuit

Section titled “4. Circuit”

A circuit is a program formalizing the statement to be proven as a system of algebraic equations (constraints).

For example, the statement “a number x is known such that x > 0 and x² = 4” has the solution x = 2. A circuit proves knowledge of such an x without revealing the number 2 itself.

In zkpool-mesh, the withdrawal circuit enforces five statements simultaneously:

  1. C1 (nullifier validity): a secret number nullifier is known such that hash_1(nullifier) == nullifier_hash.
  2. C2 (recipient binding): a secret note_secret is known binding the proof to a specific recipient address: hash_2(note_secret, recipient) == recipient_binding.
  3. C3 (Merkle tree inclusion): the commitment computed as hash_3(nullifier, secret, amount) belongs to the Merkle tree with public root.
  4. C4 (split sum conservation): the sum of the three deposit shares equals the aggregate deposit amount: splits + splits + splits == total_amount.
  5. C5 (note denomination match): the withdrawn amount matches the share at note_index: splits[note_index] == amount (subject to note_index < 3).

5. Public and Private Inputs

Section titled “5. Public and Private Inputs”

Circuit inputs are divided into two categories:

Public inputs

Section titled “Public inputs”

Known to both prover and verifier (submitted on-chain in the Solana transaction).
The withdrawal circuit defines 6 public inputs:

  • root — Merkle tree root recorded in the pool’s root history.
  • nullifier_hash — public hash of the nullifier to prevent double-spending.
  • recipient — SOL recipient address (reduced modulo the BN254 scalar field).
  • recipient_binding — recipient binding hash (protects against transaction front-running).
  • amount — denomination of the specific note being withdrawn, in lamports.
  • total_amount — aggregate amount of the original three-way deposit.

Private inputs

Section titled “Private inputs”

Known only to the proving side and never published on-chain.
The withdrawal circuit defines 7 private inputs:

  • nullifier — secret nullifier of the note.
  • secret — random secret of the note.
  • note_secret — secret used for recipient binding.
  • merkle_proof — array of 20 sibling hashes from leaf to tree root.
  • is_even — array of 20 directional flags (left or right child at each level).
  • splits — array of 3 denominations into which the deposit was split.
  • note_index — index of the current note inside splits (0, 1, or 2).

6. Witness

Section titled “6. Witness”

A witness is the complete assignment of all 13 inputs (6 public and 7 private) satisfying every constraint in the circuit.

If a circuit is a system of equations, the witness is a concrete solution. Generating a proof requires a complete witness. The witness remains exclusively on the user side: leaking private witness fields exposes the link between deposit and withdrawal.

7. Commitment

Section titled “7. Commitment”

A commitment is a cryptographic hash binding deposit note parameters in hidden form:

  • Neither nullifier, secret, nor amount can be derived from a commitment.
  • During withdrawal, the holder of the secrets proves inside the circuit knowledge of the preimage of that commitment without revealing it.

8. Nullifier

Section titled “8. Nullifier”

To prevent double-spending the same deposit note, a pair of secret nullifier and public nullifier_hash = hash_1(nullifier) is used:

  • On the first withdrawal of a note, the on-chain program derives a nullifier_record PDA from nullifier_hash and initializes that account.
  • Any attempt to withdraw the same note again must present the identical nullifier_hash (otherwise constraint C1 fails).
  • The Solana runtime sees that a nullifier_record account at that address already exists and rejects the transaction.

Thus, commitment places the note into the shared pool without revealing its owner, while nullifier_hash marks it spent without revealing which commitment in the tree was consumed.

9. Merkle Tree and Merkle Proof

Section titled “9. Merkle Tree and Merkle Proof”

A Merkle tree is a binary hash tree whose leaves store deposit commitments and whose parent nodes are computed as hash_2(left, right):

At depth 20, the tree holds up to 2^20 = 1,048,576 deposit notes while summarizing the entire set in a single 32-byte root hash.

A Merkle proof is the minimal path of 20 sibling hashes from a target leaf to the root.
For a depth-3 tree and leaf C1, the path contains just two hashes: [C0, P1].
Together with the side flags is_even, the circuit performs 20 hash steps to recompute the root and verify it against the public input root.

10. End-to-End Lifecycle in zkpool-mesh

Section titled “10. End-to-End Lifecycle in zkpool-mesh”

Step 1. Split Deposit (deposit_split)

Section titled “Step 1. Split Deposit (deposit_split)”

Frontend (browser):

  • Splits the deposited total_amount into three shares: splits, splits, splits. Используйте код с осторожностью.
  • Generates independent secrets (nullifier, secret, note_secret) for each share and computes commitment = hash_3(nullifier, secret, amount) via the Noir WASM module (@noir-lang/noir_js).
  • Stores the three secret deposit notes in browser local storage.

Frontend → On-chain program zk_pool:

  • Submits the wallet-signed deposit_split transaction.
  • The contract transfers SOL into the pool vault account, appends all three commitments to the Merkle tree, and updates the root history.

Backend indexer + Merkle service:

  • The indexer in services/backend observes the on-chain deposit event, persists the commitments in PostgreSQL, and forwards them to services/merkle to update the off-chain Merkle tree.

Step 2. Withdrawing a Single Note (withdraw)

Section titled “Step 2. Withdrawing a Single Note (withdraw)”

Frontend (browser):

  • Selects an unspent deposit note and specifies the recipient address.
  • Computes public values nullifier_hash = hash_1(nullifier) and recipient_binding = hash_2(note_secret, recipient) via the Noir WASM module, reducing the recipient address modulo the BN254 field prime.
  • Assembles the full input payload (all 6 public and 7 private inputs) and sends it to POST /api/withdraw.

Frontend → Backend → Merkle service:

  • Requests the leaf index (/api/commitments), current root (/api/root), and Merkle path (/api/proof).
  • The backend gateway (services/backend) fetches merkle_proof and is_even flags from services/merkle.

Backend → Prover service:

  • Validates the payload and proxies the request to services/prover (POST /prove).
  • Inside prover, nargo execute computes the binary witness and sunspot prove generates the Groth16 proof (388 bytes) along with the serialized public witness (204 bytes).

Frontend → On-chain program zk_pool → Verifier:

  • Upon receiving the proof from the backend, the frontend constructs and submits the withdraw transaction to Solana.
  • The zk_pool program verifies that root exists in pool history, invokes the on-chain verifier (gnark-solana) via CPI, initializes the nullifier_record account, and transfers the note’s SOL denomination to recipient.
