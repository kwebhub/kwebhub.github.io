Этап 2: ZK-схемы на Noir и конвейер Sunspot

Этап 2 определяет криптографическое ядро проекта zkpool-mesh:

  • схемы доказательств с нулевым разглашением на языке Noir,
  • единый контракт публичных и приватных входов spec.json,
  • конвейер Sunspot, превращающий промежуточное представление ACIR в on-chain программу-верификатор Groth16 для Solana.

1. Почему Noir и Poseidon2

Заголовок раздела «1. Почему Noir и Poseidon2»

Выбор стека Noir + Sunspot решает две ключевые задачи приватного пула на Solana:

  • Единый ACIR для браузера, Node.js и Rust:
    скомпилированный JSON-артефакт схемы (hash2.json, hashes.json, withdrawal.json) исполняется в браузере и в сервисе дерева Меркла через @noir-lang/noir_js, а на сервере доказательств — через nargo execute и sunspot prove.
    Такой подход исключает расхождение хешей между разными языками программирования.
  • Арифметика Poseidon2 поверх кривой BN254:
    классические битовые хеш-функции вроде SHA-256 требуют сотен ограничений (constraints) на каждый вызов внутри арифметической схемы.
    Poseidon2 работает напрямую в конечном поле BN254 с параметрами состояния t = 4, rate = 3, capacity = 1, сокращая размер системы ограничений и время генерации доказательства на порядки.
  • Компактность Groth16 для транзакций Solana:
    размер транзакции Solana ограничен 1232 байтами.
    Протокол Groth16 (реализованный в Sunspot поверх gnark-solana) даёт фиксированный размер доказательства в 388 байт и быструю верификацию через системные прекомпилы alt_bn128.

2. Единый источник истины: circuits/withdrawal/spec.json

Заголовок раздела «2. Единый источник истины: circuits/withdrawal/spec.json»

Файл circuits/withdrawal/spec.json фиксирует контракт схемы на уровне данных:

  • Параметры схемы:
    • имя withdrawal,
    • точка входа main,
    • глубина дерева Меркла tree_depth = 20,
    • поддержка сплита депозита split_count = 3,
    • количество публичных входов nr_public_inputs = 6.
  • 6 публичных входов (192 байта в секции witness):
    1. root (field, 32 байта, BN254 big-endian) — актуальный или исторический корень дерева Меркла из кольцевого буфера пула.
    2. nullifier_hash (field, 32 байта) — hash_1(nullifier), используемый как seed PDA-записи потраченной записки.
    3. recipient (pubkey, 32 байта) — публичный ключ получателя Solana, приведённый по модулю простого числа поля BN254.
    4. recipient_binding (field, 32 байта) — hash_2(note_secret, recipient), криптографически привязывающий доказательство к конкретному получателю и защищающий от подмены адреса (front-running).
    5. amount (u64, 8 байт, выровнено по правому краю в 32-байтном слове) — сумма вывода текущей записки в lamports.
    6. total_amount (u64, 8 байт, выровнено по правому краю в 32-байтном слове) — совокупная сумма депозита по всем трём долям сплита.
  • 7 приватных входов:
    1. nullifier,
    2. secret,
    3. note_secret,
    4. массив соседних хешей merkle_proof,
    5. массив флагов направления is_even,
    6. вектор долей депозита splits
    7. индекс текущей записки note_index (u32).
  • 5 ограничений схемы (C1–C5):
    1. C1: hash_1(nullifier) == nullifier_hash
    2. C2: hash_2(note_secret, recipient) == recipient_binding
    3. C3: compute_merkle_root(hash_3(nullifier, secret, amount), merkle_proof, is_even) == root
    4. C4: splits[0] + splits[1] + splits[2] == total_amount
    5. C5: splits[note_index] == amount (после проверки note_index < 3)
  • Формат заголовка и буфера witness (204 байта): 12-байтный заголовок (nr_public_inputs как u32 BE, зарезервированный ноль u32 BE, повтор nr_public_inputs как u32 BE) + 6 × 32 = 192 байта публичных входов.

3. Валидация спецификации (scripts/validate-spec)

Заголовок раздела «3. Валидация спецификации (scripts/validate-spec)»

Для автоматической проверки внутренней согласованности spec.json используется Rust-утилита scripts/validate-spec (цель make validate-spec), проверяющая 17 правил:

Валидатор сверяет версию схемы, глубину дерева (20), размерность сплита (3), уникальность имён публичных входов, сумму сырых байтов (144) и слотов witness (192), общий размер буфера (204 байта), наличие всех пяти ограничений (C1–C5), запрет функции hash_4 (которая обнулила бы capacity перестановки Poseidon2) и список потребителей (prover, merkle, web).

4. Четыре пакета Noir (circuits/)

Заголовок раздела «4. Четыре пакета Noir (circuits/)»

Код схем разделён на общую библиотеку и три исполняемых пакета:

  1. circuits/poseidon (type = “lib”):
    реализует функции hash_1, hash_2 и hash_3 поверх std::hash::poseidon2_permutation с дополнением нулями до 4 элементов.
    Функция hash_4 намеренно запрещена, чтобы сохранять ненулевой слот capacity.
    Пакет покрыт 11 модульными тестами (детерминизм, некоммутативность и документированные свойства zero-padding).
  2. circuits/hash2 (type = “bin”):
    обёртка над hash_2(left, right) -> pub Field.
    Компилируется в hash2.json для вычисления узлов дерева Меркла в services/merkle и на фронтенде (5 тестов).
  3. circuits/hashes (type = “bin”):
    вычисляет пару (commitment, nullifier_hash) из (nullifier, secret, amount) для проверки записки перед отправкой депозита (9 тестов).
  4. circuits/withdrawal (type = “bin”):
    основная схема вывода с модулями merkle_tree.nr (подъём от листа к корню по 20 уровням с учётом флага стороны is_even[i]) и test_witness.nr (генератор контрольных входов).
    Покрыта 24 тестами, проверяющими каждое ограничение C1–C5, выход note_index за границы массива и полный проход по дереву.

5. Синхронизация ACIR-артефактов (scripts/sync-circuits)

Заголовок раздела «5. Синхронизация ACIR-артефактов (scripts/sync-circuits)»

После компиляции схем (nargo compile) бинарные JSON-файлы ACIR должны быть идентичны во всех компонентах системы:

Утилита scripts/sync-circuits поддерживает два режима:

  • make sync (sync-circuits apply) — компилирует hash2, hashes и withdrawal, вычисляет их SHA-256 и копирует актуальные артефакты в services/merkle/circuits/ и web/public/circuits/.
  • make sync-check (sync-circuits check) — режим проверки без перезаписи для CI: завершается с кодом 1, если хеш хотя бы одной копии расходится с исходным ACIR.

6. Конвейер Sunspot: от ACIR до on-chain верификатора

Заголовок раздела «6. Конвейер Sunspot: от ACIR до on-chain верификатора»

При выполнении цели make chain (модуль infra/mk/chain.mk) промежуточное представление withdrawal.json проходит через четыре шага Sunspot:

  1. sunspot compile target/withdrawal.json — разворачивает высокоуровневые операции Poseidon2 и цикл по дереву Меркла в систему ограничений R1CS/CCS (target/withdrawal.ccs).
  2. sunspot setup target/withdrawal.ccs — выполняет генерацию ключа доказательства (target/withdrawal.pk) и ключа верификации (target/withdrawal.vk). В тестовой среде setup выполняется локально; для production-развёртывания требуется многосторонняя MPC-церемония.
  3. sunspot deploy target/withdrawal.vk — компилирует Rust-крейт верификатора gnark-solana (GNARK_VERIFIER_BIN=/home/i/sunspot/gnark-solana/crates/verifier-bin) через cargo build-sbf, встраивая ключ верификации в BPF-программу target/withdrawal.so и создавая ключ программы target/withdrawal-keypair.json.
  4. solana program deploy + синхронизация ID — разворачивает верификатор в валидатор (–use-rpc), извлекает новый VERIFIER_PROGRAM_ID и автоматически записывает его в onchain/programs/zk_pool/src/constants.rs и в .env перед сборкой основного контракта zk_pool.

При обработке запроса на вывод сервис zkpool-prover выполняет обратную связку:
nargo execute формирует witness withdrawal.gz, после чего sunspot prove генерирует 388-байтное доказательство Groth16 (withdrawal.proof) и 204-байтный публичный witness (withdrawal.pw), который верифицируется на уровне протокола.

7. Проблемы и практические решения

Заголовок раздела «7. Проблемы и практические решения»
  • Переполнение поля BN254 при передаче 256-битных значений:
    простое число поля BN254 меньше 2^254, поэтому произвольный 32-байтный ключ Solana (Pubkey) нельзя передать в Field напрямую. На всех слоях (в Rust-контракте, в zkpool-prover и на фронтенде) выполняется единая редукция ключа по модулю поля BN254.
  • Парсинг больших hex-чисел в Prover.toml:
    парсер TOML в nargo пытается интерпретировать некавыченные hex-литералы как 64-битные целые и падает с ошибкой переполнения. Все значения типа Field в Prover.toml должны записываться в двойных кавычках (“0x…”).
  • Перезапись withdrawal-keypair.json при каждом sunspot deploy:
    при каждой пересборке верификатора sunspot deploy генерирует новый keypair и меняет адрес программы. Поэтому в infra/mk/chain.mk сборка верификатора строго предшествует сборке zk_pool, а новый VERIFIER_PROGRAM_ID автоматически подставляется в исходный код Rust-контракта и .env.
  • Устаревшие константы ALT_BN128_ при сборке gnark-solana:*
    при компиляции verifier-bin компилятор выводит предупреждения об использовании устаревших констант solana_bn254. Данная особенность относится к upstream-крейту gnark-solana и не влияет на сборку .so и корректность проверки парных спариваний.
