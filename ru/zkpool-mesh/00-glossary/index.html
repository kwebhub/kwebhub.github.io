Глоссарий

Справочник терминов, встречающихся в проекте zkpool-mesh.
Термины отсортированы по тематическим разделам и описаны без жаргона.

1. Криптография с нулевым разглашением (ZK)

Заголовок раздела «1. Криптография с нулевым разглашением (ZK)»

ZK proof (доказательство с нулевым разглашением)

Заголовок раздела «ZK proof (доказательство с нулевым разглашением)»

Криптографический способ доказать знание секрета, не раскрывая сам секрет.

В zkpool-mesh пользователь доказывает, что владеет секретами одной из записок депозита в пуле, не раскрывая, какой именно.
Это разрывает связь между транзакцией депозита и транзакциями вывода.

Circuit (схема, ZK-схема)

Заголовок раздела «Circuit (схема, ZK-схема)»

Программа, описывающая доказываемое утверждение.
Состоит из публичных входов, приватных входов и набора математических ограничений (constraints).

В проекте используется схема withdrawal, проверяющая пять утверждений (C1–C5).

Публичный вход (public input)

Заголовок раздела «Публичный вход (public input)»

Значение, известное и доказывающему (prover), и проверяющему (verifier).
В Noir объявляется ключевым словом pub.

В схеме withdrawal 6 публичных входов:
root, nullifier_hash, recipient, recipient_binding, amount, total_amount.

Приватный вход (private input)

Заголовок раздела «Приватный вход (private input)»

Значение, известное только доказывающему (prover) и скрытое от проверяющего.
В Noir объявляется без pub.

В схеме withdrawal 7 приватных входов:
nullifier, secret, note_secret, merkle_proof[20], is_even[20], splits[3], note_index.

Witness (свидетельство)

Заголовок раздела «Witness (свидетельство)»

Полный набор входных данных для схемы (как публичных, так и приватных), подставляемый в ограничения.
Без witness невозможно сгенерировать доказательство.

Constraint (ограничение)

Заголовок раздела «Constraint (ограничение)»

Алгебраическое уравнение, которому должны удовлетворять входы схемы.
Если хотя бы одно ограничение нарушено, валидное доказательство построить невозможно.

В схеме withdrawal 5 логических ограничений:

  • C1: hash_1(nullifier) == nullifier_hash.
  • C2: hash_2(note_secret, recipient) == recipient_binding.
  • C3: compute_merkle_root(hash_3(nullifier, secret, amount), merkle_proof, is_even) == root.
  • C4: splits[0] + splits[1] + splits[2] == total_amount.
  • C5: splits[note_index] == amount (при условии note_index < 3).

Prover (доказывающий)

Заголовок раздела «Prover (доказывающий)»

Сторона, вычисляющая witness и генерирующая ZK-доказательство.
В проекте эту роль выполняет сервис services/prover на базе Rust и Sunspot.

Verifier (проверяющий)

Заголовок раздела «Verifier (проверяющий)»

Сторона, проверяющая корректность доказательства по публичным входам.
В проекте это отдельная on-chain программа Solana (gnark-solana).

Commitment (обязательство)

Заголовок раздела «Commitment (обязательство)»

Криптографический хеш, фиксирующий параметры записки депозита без их раскрытия:

По значению commitment невозможно восстановить исходные числа, но владелец секретов может доказать их соответствие листу в дереве Меркла.

Nullifier (обнулитель)

Заголовок раздела «Nullifier (обнулитель)»

Секретное число, однозначно связанное с конкретной запиской депозита и используемое для защиты от повторного вывода (double-spend).
Хранится только на стороне пользователя.

Nullifier hash

Заголовок раздела «Nullifier hash»

Публичный хеш от nullifier (nullifier_hash = hash_1(nullifier)), передаваемый в блокчейн при выводе средств.
Используется как seed для PDA-аккаунта NullifierRecord и как ключ потраченной записки в базе данных.

2. Хеш-функции и структуры данных

Заголовок раздела «2. Хеш-функции и структуры данных»

Хеш-функция

Заголовок раздела «Хеш-функция»

Детерминированная односторонняя функция, преобразующая входные данные произвольного размера в число фиксированной длины.
Устойчива к поиску прообраза и коллизий.

Poseidon2

Заголовок раздела «Poseidon2»

Алгебраическая хеш-функция, спроектированная специально для ZK-схем.
Работает напрямую с элементами конечного поля с помощью сложений и умножений, благодаря чему требует на порядок меньше ограничений в схеме, чем SHA-256 или Keccak.

В Noir вызывается через встроенную функцию poseidon2_permutation с шириной состояния t = 4.

Перестановка (permutation)

Заголовок раздела «Перестановка (permutation)»

Обратимая функция перемешивания состояния фиксированного размера.
В Poseidon2 применяется к массиву из 4 элементов поля (t = 4).

Rate и capacity

Заголовок раздела «Rate и capacity»

Параметры губчатой (sponge) конструкции хеширования при ширине состояния t = r + c = 4:

  • Rate (r = 3) — количество слотов состояния, используемых для поглощения входных данных.
  • Capacity (c = 1) — резервный слот, обеспечивающий криптографическую стойкость против коллизий.

Из-за r = 3 в проекте определены функции hash_1, hash_2 и hash_3, но не hash_4.

Zero-padding (дополнение нулями)

Заголовок раздела «Zero-padding (дополнение нулями)»

Заполнение неиспользуемых слотов rate нулями:

  • hash_1(x) → состояние [x, 0, 0, 0]
  • hash_2(x, y) → состояние [x, y, 0, 0]
  • hash_3(x, y, z) → состояние [x, y, z, 0]

BN254

Заголовок раздела «BN254»

Эллиптическая кривая, используемая в Groth16, Noir и прекомпилах Solana (alt_bn128).
Модуль скалярного поля:

Значения типа Field в Noir лежат в диапазоне от 0 до p - 1 (примерно 2^254).
Поскольку 32-байтный публичный ключ Solana (256 бит) может превышать модуль поля, перед передачей в схему он приводится по модулю p.

Merkle tree (дерево Меркла)

Заголовок раздела «Merkle tree (дерево Меркла)»

Двоичное дерево хешей, где листья содержат commitments депозитов, а каждый родительский узел равен hash_2(left, right).
Изменение любого листа меняет корневой хеш дерева.

Глубина дерева в проекте равна 20 (до 2^20 = 1 048 576 листьев).

Merkle proof

Заголовок раздела «Merkle proof»

Путь из 20 соседних хешей (siblings) от целевого листа до корня дерева, позволяющий доказать включение листа в дерево без раскрытия его позиции.

Merkle root

Заголовок раздела «Merkle root»

Корневой хеш дерева Меркла, компактно представляющий всё множество депозитов.
On-chain программа хранит кольцевой буфер из 10 последних корней (ROOT_HISTORY_SIZE = 10), чтобы параллельные депозиты не инвалидировали уже формируемые доказательства.

is_even (флаг стороны)

Заголовок раздела «is_even (флаг стороны)»

Массив из 20 булевых флагов для каждого уровня дерева Меркла: значение true означает, что текущий узел является левым потомком (hash_2(current, sibling)), false — правым (hash_2(sibling, current)). Флаг необходим, так как функция hash_2 не коммутативна.

3. Noir и ZK-схемы

Заголовок раздела «3. Noir и ZK-схемы»

Noir

Заголовок раздела «Noir»

Предметно-ориентированный язык программирования для описания ZK-схем с синтаксисом, близким к Rust.
Компилируется в промежуточное представление ACIR.

Nargo

Заголовок раздела «Nargo»

Инструмент командной строки и менеджер пакетов для Noir (аналог Cargo в Rust).
Основные команды: nargo test, nargo compile, nargo execute.

ACIR (Abstract Circuit Intermediate Representation)

Заголовок раздела «ACIR (Abstract Circuit Intermediate Representation)»

Платформонезависимое промежуточное представление скомпилированной схемы, содержащее описание входов, ограничений и байткод для вычисления свидетельства.
Сохраняется в JSON-файлах (например, withdrawal.json).

Nargo.toml и main.nr

Заголовок раздела «Nargo.toml и main.nr»

Манифест пакета Noir (Nargo.toml, задаёт тип пакета bin или lib и зависимости) и исходный файл точки входа схемы (main.nr с функцией main).

Field

Заголовок раздела «Field»

Базовый числовой тип в Noir, представляющий элемент скалярного поля кривой BN254.
Арифметика выполняется по модулю простого числа p.

Const generics

Заголовок раздела «Const generics»

Параметризация функций и массивов константами времени компиляции (например, compute_merkle_root), позволяющая переиспользовать код для деревьев разной глубины.

4. Groth16 и Sunspot

Заголовок раздела «4. Groth16 и Sunspot»

Groth16

Заголовок раздела «Groth16»

Система неинтерактивных доказательств с нулевым разглашением (zk-SNARK), отличающаяся постоянным малым размером доказательства и быстрой проверкой, что делает её пригодной для верификации внутри транзакций Solana.

Trusted setup и MPC-церемония

Заголовок раздела «Trusted setup и MPC-церемония»

Однократная генерация ключей доказательства (proving key) и верификации (verifying key) для конкретной схемы.
В процессе возникают промежуточные секретные параметры (toxic waste).
В демонстрационной среде setup выполняется локально; для боевого развёртывания требуется многосторонняя церемония (MPC), исключающая знание toxic waste кем-либо из участников.

CCS (Constraint System)

Заголовок раздела «CCS (Constraint System)»

Низкоуровневое представление системы ограничений (файл withdrawal.ccs), получаемое из ACIR перед генерацией ключей Groth16.

Proving key (.pk) и Verifying key (.vk)

Заголовок раздела «Proving key (.pk) и Verifying key (.vk)»
  • Proving key (withdrawal.pk) — ключ для генерации доказательств, используемый сервисом prover.
  • Verifying key (withdrawal.vk) — компактный публичный ключ проверки, вшиваемый в on-chain программу верификатора.

Sunspot

Заголовок раздела «Sunspot»

Инструментарий для связки Noir и Solana (на базе gnark-solana).
Выполняет компиляцию ACIR в CCS (sunspot compile), генерацию ключей (sunspot setup), сборку и деплой on-chain верификатора (sunspot deploy), а также генерацию доказательств (sunspot prove).

Proof (.proof) и Public witness (.pw)

Заголовок раздела «Proof (.proof) и Public witness (.pw)»
  • Proof — бинарное доказательство Groth16 (388 байт в актуальной конфигурации проекта).
  • Public witness — сериализованные публичные входы (204 байта: 12-байтный заголовок и шесть 32-байтных полей), передаваемые верификатору вместе с доказательством.

5. Solana

Заголовок раздела «5. Solana»

Program и BPF

Заголовок раздела «Program и BPF»

Смарт-контракт в Solana называется программой, хранится в исполняемом аккаунте в виде байткода BPF (Berkeley Packet Filter) и компилируется из Rust командой cargo build-sbf.
В проекте задействованы две программы: zk_pool и verifier.

Program ID и ProgramData

Заголовок раздела «Program ID и ProgramData»

Program ID — неизменяемый публичный адрес программы.
Исполняемый байткод обновляемой программы хранится в отдельном связанном аккаунте ProgramData, что позволяет обновлять логику без смены адреса программы (пока активен upgrade authority).

Rent (аренда)

Заголовок раздела «Rent (аренда)»

Минимальный баланс в lamports, необходимый для хранения данных аккаунта в состоянии сети (rent-exempt).

PDA (Program Derived Address)

Заголовок раздела «PDA (Program Derived Address)»

Используйте код с осторожностью.
Детерминированный адрес аккаунта без приватного ключа, вычисляемый из набора текстовых или бинарных сидов (seeds) и Program ID.
Подписывать операции от имени PDA может только владеющая им программа.
В zk_pool используются три типа PDA: • pool — seeds: [“pool3”]. • vault — seeds: [“vault3”, pool]. • nullifier_record — seeds: [“nullifier_record”, pool, nullifier_hash].

CPI (Cross-Program Invocation)

Заголовок раздела «CPI (Cross-Program Invocation)»

Межпрограммный вызов в Solana.
Инструкция withdraw программы zk_pool вызывает программу верификатора через CPI для проверки Groth16-доказательства.

Transaction, Instruction и Discriminator

Заголовок раздела «Transaction, Instruction и Discriminator»

Транзакция объединяет одну или несколько атомарных инструкций.
Каждая инструкция Anchor начинается с 8-байтного дискриминатора — префикса SHA-256 от имени инструкции, по которому программа маршрутизирует вызов.

6. Доменные термины проекта

Заголовок раздела «6. Доменные термины проекта»

Deposit note (записка депозита)

Заголовок раздела «Deposit note (записка депозита)»

Набор секретных параметров (nullifier, secret, note_secret, amount, commitment), позволяющий вывести соответствующую часть депозита.
При вызове deposit_split сумма депозита делится на три части (SPLIT_COUNT = 3), в дерево Меркла добавляются три commitment, а пользователь получает три независимые записки для вывода средств частями.

Pool и Vault

Заголовок раздела «Pool и Vault»
  • Pool — аккаунт состояния пула (PDA [“pool3”]), хранящий корень дерева Меркла, историю последних 10 корней и счётчик листьев.
  • Vault — системный аккаунт-хранилище (PDA [“vault3”, pool]), удерживающий депонированные SOL. Разделение состояния и баланса предотвращает смешивание данных с переводимыми средствами.

recipient_binding и защита от front-running

Заголовок раздела «recipient_binding и защита от front-running»

Front-running — перехват валидной транзакции в мемпуле и отправка копии с подменённым адресом получателя и повышенной комиссией.
Поле recipient_binding = hash_2(note_secret, recipient) криптографически связывает доказательство с конкретным адресом получателя: при подмене recipient не выполняется ограничение C2 и транзакция отклоняется.

Double-spend (двойное расходование)

Заголовок раздела «Double-spend (двойное расходование)»

Попытка вывести одну и ту же записку депозита повторно.
Блокируется созданием PDA-аккаунта nullifier_record при первом выводе: повторная транзакция с тем же nullifier_hash падает на уровне рантайма Solana.

spec.json и validate-spec

Заголовок раздела «spec.json и validate-spec»

spec.json (circuits/withdrawal/spec.json) — единый источник истины, описывающий публичные и приватные входы, размеры массивов и разметку public witness.
Утилита validate-spec проверяет внутреннюю непротиворечивость спецификации до сборки сервисов.

sync-circuits

Заголовок раздела «sync-circuits»

CLI-утилита на Rust (scripts/sync-circuits/), синхронизирующая скомпилированные ACIR-файлы из circuits/ в сервисы-потребители (services/merkle/circuits/ и web/public/circuits/).
В режиме –check используется в CI для блокировки рассинхронизации артефактов.

7. Инструменты разработки

Заголовок раздела «7. Инструменты разработки»

Rust и Cargo

Заголовок раздела «Rust и Cargo»

Основной язык и система сборки для on-chain программы zk_pool, бэкенда, сервиса prover, CLI-утилит и интеграционных тестов на LiteSVM.

Anchor и IDL

Заголовок раздела «Anchor и IDL»

Фреймворк для разработки программ Solana на Rust.
Автоматически генерирует JSON-описание интерфейса программы — IDL (Interface Description Language), используемое клиентами и тестами для формирования инструкций.

@solana/kit

Заголовок раздела «@solana/kit»

Современный модульный TypeScript SDK для взаимодействия с RPC Solana, формирования транзакций и работы с адресами во фронтенде.

Node.js, pnpm, Vite, Vue 3, Pinia

Заголовок раздела «Node.js, pnpm, Vite, Vue 3, Pinia»
  • Node.js 24 и pnpm 12 — среда выполнения и менеджер пакетов для merkle-сервиса и фронтенда.
  • Vite, Vue 3 и Pinia — сборщик, реактивный UI-фреймворк и менеджер состояния веб-приложения.

@noir-lang/noir_js

Заголовок раздела «@noir-lang/noir_js»

JavaScript/WASM-библиотека выполнения скомпилированных схем Noir.
Используется в merkle-сервисе для вычисления хешей Poseidon2 и во фронтенде для генерации witness в браузере.

Docker и Compose

Заголовок раздела «Docker и Compose»

Среда контейнеризации проекта, разделённая на четыре специализированных образа и контейнера: zkpool-mesh (бэкенд, prover, сборка контрактов и схем), zkpool-merkle (сервис дерева Меркла), zkpool-web (фронтенд на nginx) и zkpool-validator (локальный валидатор Solana).

Prometheus и Grafana

Заголовок раздела «Prometheus и Grafana»

Стек мониторинга: Prometheus собирает метрики с микросервисов, Grafana визуализирует их на дашбордах.

SHA-256

Заголовок раздела «SHA-256»

Криптографическая хеш-функция, используемая в системе чекпоинтов (.checkpoints/) для побайтового контроля идентичности артефактов между этапами разработки.
